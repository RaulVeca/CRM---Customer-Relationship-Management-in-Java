Abstract
This thesis presents a full-stack Customer Relationship Management (CRM) system devel-
oped for the TrainingIT platform, serving as a practical framework for analyzing software architecture
and object-oriented design patterns. The architecture consists of two deeply decoupled subsystems
connected via a strict REST/JSON contract. The autonomous Java backend (Spring Boot 3.5)
manages its own schema, HikariCP connection pool, and native JDBC transactions, while the fron-
tend operates as a standalone Next.js 16 single-page application built with minimal external de-
pendencies. Furthermore, the implementation integrates classic Gang of Four and enterprise design
patterns(cid:22)including Facade, Singleton, Command, Observer, Factory, Strategy, and Chain
of Responsibility(cid:22)collaborating seamlessly within a single live transactional (cid:29)ow. Concluding with
a transparent self-evaluation, this work explicitly documents its own architectural limitations to serve
as a foundation for future development.
Keywords: CRM, software architecture, design patterns, Spring Boot, Next.js, REST API, JDBC,
separation of concerns.

1 Introduction
In the contemporary techno-economic and industrial ecosystem, Customer Relationship Manage-
ment (CRM) systems have evolved beyond the rudimentary stage of simple contact logs to become
central pillars of an organization’s operational and decision-making strategies. These platforms syn-
ergistically integrate complex sales management work(cid:29)ows, multichannel communication channels,
advanced analytical reporting mechanisms, and(cid:22)to an increasingly signi(cid:28)cant extent(cid:22)subsystems
based on Arti(cid:28)cial Intelligence. For a business entity specializing in IT training, such as the Train-
ingIT platform, this type of software infrastructure must orchestrate(cid:22)in a multifaceted manner(cid:22)
everything from granular interactions with individual learners to large-scale corporate transactions,
as well as the dynamic course catalog, enrollment processes, automated tax invoicing, and technical
support work(cid:29)ows.
The intrinsic motivation for this research stems from a dual structural necessity: The pragmatic
dimension: The imperative to build a fully functional application grounded in the operational realities
of a complete business cycle(cid:22)analytically tracing the path from an anonymous visitor browsing the
public catalog to the completion of enrollment and the automatic generation of the associated tax
documents.
The academic dimension: The need to use this software artifact as a genuine empirical vehicle for
dissecting complex software architectures and for the deliberate, applied implementation of Object-
Oriented Design Patterns. Too often, these structural patterns are illustrated in isolation, using
arti(cid:28)cial or overly simpli(cid:28)ed examples; The present work aims to demonstrate their organically in-
tertwined viability within a real-world system, where each pattern addresses and resolves a speci(cid:28)c
runtime vulnerability, thereby avoiding their introduction based on purely theoretical considerations.
From a pedagogical perspective, the project aims to achieve clearly de(cid:28)ned methodological mile-
stones:
(cid:136) Deep assimilation of the "Separation of Concerns" principle: Demonstrating how a precise lay-
ering of the codebase results in a transparent, fully testable, and easily maintainable system
[22, 31].
(cid:136) Applied study of classic (Gang of Four) and Enterprise design patterns [16, 15]: A detailed
analysis of interactions between patterns such as Singleton, Facade, Command, Repository/DAO,
Factory, Observer, Strategy, and Chain of Responsibility. The objective goes beyond mere iden-
ti(cid:28)cation by name, focusing instead on how these structures collaborate polymorphically within
the same execution thread, playing a decisive role in decoupling components.
(cid:136) Understanding asynchronous and decoupled communication mechanisms: Investigating the in-
terface between two fully autonomous applications(cid:22)a Java backend and a Next.js frontend(cid:22)
via a strict REST/JSON contract, complemented by the implementation of modern real-time
synchronization technologies (such as Server-Sent Events/SSE) and state management that
avoids intrusive global libraries.
(cid:136) Cultivating a critical mindset and epistemological integrity in software engineering [27]: Devel-
oping the ability to honestly identify, map, and document the inherent discrepancies between
ideal theoretical models and the constraints of actual technological implementation.
1.1 Application Design Objectives
From a software systems engineering perspective, the primary objective was to build a fully autonomous
Java backend where the web framework served solely as a thin peripheral layer for interface exposure,
keeping the business logic structurally independent. Speci(cid:28)cally, the aim was for the domain core
to independently manage its own relational schema, active connection pool, and transaction bound-
aries, theoretically allowing it to run outside any web container. The backend subsystem was built on

Spring Boot 3.5, with persistence handled in MariaDB via native JDBC statements and a Hikar-
iCP connection pool; the use of an ORM layer was programmatically avoided to maintain absolute,
deterministic control over query performance.
A second major objective focused on the radical decoupling of the graphical interface. The fron-
tend subsystem was designed as a standalone Single-Page Application(cid:22)implemented using Next.js 16
(App Router), $\rightarrow$, and TypeScript 5(cid:22)communicating with the server exclusively via
REST/JSON messages without sharing any session state. This disjoint architecture allows both com-
ponents to evolve completely independently. Additionally, the design incorporated advanced services(cid:22)
such as contextual recommendations, virtual sales assistants, chatbot modules, and dynamic language
localization(cid:22)by interfacing with an external Arti(cid:28)cial Intelligence engine; however, this engine was
designed as a strictly optional module capable of graceful degradation, thereby preventing application
failure in the event of third-party API unavailability.

2 State of the Art
Modern CRM systems provide tools for managing customer information, sales activities, communica-
tion and business opportunities. Popular solutions such as Salesforce, HubSpot, Zoho CRM and
Odoo o(cid:27)er extensive functionality, cloud access and integration with external services. However, these
platforms can be complex or expensive for smaller organizations.
In the current economic and technological landscape, de(cid:28)ned by accelerated digitalization, CRM
(Customer Relationship Management) platforms have become fundamental pillars of business strate-
gies. These systems have surpassed the stage of simple contact management, evolving into complex
business intelligence solutions that integrate operational work(cid:29)ows, predictive analytics, and auto-
mated decision-making systems. The preference for scalable, customizable solutions that are indepen-
dent of major vendors has stimulated the rise of open-source alternatives, which guarantee full control
over the codebase and enhanced adaptability to pre-existing digital infrastructures.
Customer Relationship Management(cid:22)or CRM, as it is universally known in the industry (and
there is no point in pretending otherwise)(cid:22)is not, ontologically speaking, merely a software package
one implements via "plug-and-play" to instantly solve a problem. Rather, it represents a strate-
gic paradigm(cid:22)a cognitive and operational stance adopted by an organization toward its consumer
ecosystem(cid:22)while the IT infrastructure, however algorithmically advanced, serves only *ex post* as an
enabler of this vision. This paper is premised on precisely this axiom: the thesis that a customer whose
behavior is deeply mapped, who is actively engaged and retained for the long term, translates(cid:22)sooner
or later (usually later, given conversion cycles)(cid:22)into optimized ROI (Return on Investment) and
sustainable pro(cid:28)tability. Conceptually, it is a simple equation; operationally, a formidable challenge.
If we look back analytically, the (cid:28)eld’s evolutionary trajectory has been truly spectacular, even
though, at a micro level(cid:22)caught up in daily operations(cid:22)such paradigm shifts often go unnoticed. In
the 1980s and 90s, the conversation centered exclusively on Sales Force Automation (SFA)(cid:22)essentially
rather rudimentary IT architectures (and I say this not pejoratively, but simply to highlight their
nascent stage). Their scope was limited to managing contact entities, opportunities, and the sales
pipeline(cid:22)and nothing more. They essentially mitigated administrative process redundancy and stan-
dardized the sales funnel; that was the extent of their utility. Subsequently, with the arrival of the
2000s, we witnessed a systemic maturation: CRM transcended departmental sales boundaries, inte-
grating marketing and post-sales technical support across the board; e(cid:27)ectively, it captured the entire
customer lifecycle(cid:22)from the initial touchpoint (a (cid:28)rst sales-oriented "hello") to, say, in an ideal loy-
alty scenario, the tenth repeat purchase. It is an eminently holistic perspective, as the document so
elegantly articulates.
The 2010(cid:21)2020 decade orchestrated the transition toward cloud computing architectures and the
Social CRM model(cid:22)marking an in(cid:29)ection point fully validated by the text: the cloud has irreversibly
democratized access to technology. What did this mean, precisely? It meant that one was no longer
constrained by enterprise status or exorbitant CAPEX budgets to maintain a high-performance CRM
instance; barriers to entry collapsed, horizontal scalability became the norm, and social networks began
injecting a previously inaccessible volume of unstructured data into the system(cid:22)the digital footprint
and behavioral metadata that users generate inherently, often quite involuntarily. And what about the
present? Today, we are witnessing a fundamental recon(cid:28)guration driven by Arti(cid:28)cial Intelligence (AI),
machine learning algorithms, and predictive modeling. We are no longer simply analyzing transactional
databases that passively store historical records; instead, we are working with neural systems capable(cid:22)
albeit with varying degrees of accuracy, naturally, yet undeniably capable(cid:22)of extrapolating patterns
and probabilistically anticipating what is to come.
2.1 The Architecture of a Modern CRM: A Layered Breakdown [4, 24]
At this point, the discussion takes a sharp turn into technical territory(cid:22)and rightly so. A modern
CRM no longer adheres to the monolithic paradigm; to be clear, it is no longer that massive, opaque,
and indivisible block where refactoring a single feature e(cid:27)ectively requires tearing the entire house
10

===== PDF PAGE 11 =====
down to its foundations. Far from it. Today, we are dealing with systems that are inherently modular
and scalable, built upon microservices architectures and designed with a speci(cid:28)c premise in mind: the
ability to decouple and replace a module without causing the entire software edi(cid:28)ce to shudder or
collapse. Broadly speaking, this architecture is organized into three layers of abstraction.
2.1.1 The Presentation Layer (The Frontend) [23]
This is the graphical interface(cid:22)essentially the point of contact with the human user. Here, we en-
counter a rather harsh operational reality(cid:22)one that the work in question lays out without sugarcoating:
you might have the most robust inference engine running underneath, but if the UI (User Interface) is
hostile or cognitively overwhelming, users simply develop resistance; the battle for adoption is won or
lost right here, down to the last millimeter. That is precisely why there is such an aggressive push today
toward omnichannel experiences, responsive design, native mobile solutions, or(cid:22)where appropriate(cid:22)
Progressive Web Apps (PWAs). From a strictly technical standpoint, we are talking about frameworks
like React, Angular, or Vue(cid:22)and, naturally, about those interactive analytical dashboards that take
massive volumes of data, run them through aggregation (cid:28)lters, and visually condense them into a few
key performance indicators that can be deciphered at a single glance. As for mobility, solutions like
React Native or Flutter are employed speci(cid:28)cally to ensure a consistent experience(cid:22)an isomorphic
one(cid:22)regardless of the device the client is holding.
2.1.2 The Business Logic Layer (The Core)
The operational heart(cid:22)or processing nucleus, however one chooses to label it. This is where the center
of gravity truly lies: procedural work(cid:29)ows, routing rules, algorithms, and complex work(cid:29)ow engines
that capture and automate recurring transactional tasks, alongside advanced noti(cid:28)cation systems and
triggers designed to alert you proactively before a process breakdown occurs. This layer also houses
the analytics modules that render KPIs in real-time and(cid:22)crucially(cid:22)orchestrates interoperability with
the external ecosystem (such as ERPs and e-commerce platforms) via REST or GraphQL APIs. It
represents a conceptual decoupling inspired by the "Headless" approach(cid:22)a form of architectural free-

3 Software Design
3.1 Overview
The architecture of the CRM system developed for the TrainingIT platform is grounded in the prin-
ciple of Separation of Concerns (SoC) and the strict segregation of roles between human actors and
systemic agents. This architectural decision is essential for ensuring the system’s long-term scalabil-
ity, maintainability, and security. By automating recurring operational work(cid:29)ows and implementing
a Role-Based Access Control (RBAC) model, the system assigns each user only the necessary privi-
leges (Principle of Least Privilege). This approach optimizes user interface performance and minimizes
database-level vulnerabilities [29, 22].
At the core of human interactions lies a hierarchical permission inheritance model. Every user
begins with the status of "Visitor" (unauthenticated user), possessing read-only access to the public
catalog. Upon authentication, the entity is granted an expanded set of rights. Within the client
portfolio, a fundamental architectural distinction is drawn between the "Learner" (the B2C entity(cid:22)
the end consumer of educational resources) and the "B2B Manager" (the representative of a legal
entity).
The B2B Manager role is intrinsic to the enterprise-oriented business model, entailing responsibility
for bulk purchases and license distribution. Their relationship with a(cid:30)liated learners is one of structural
aggregation, supported by an analytics dashboard for monitoring performance metrics (KPIs) at the
cohort level. Thus, while the Learner navigates the cognitive acquisition process, the B2B Manager
oversees the return on investment (ROI) at the organizational level [29, 22].
From an internal operational perspective, the dichotomy between the Administrator and the Trainer
illustrates the decoupling of operational governance processes from pedagogical activity. The Adminis-
trator holds superuser privileges regarding commercial parameters, system con(cid:28)gurations, and pricing
policies. To prevent the administrative node from becoming a performance bottleneck, the system
delegates content delivery responsibilities to the Trainer. The latter operates within a restricted scope,
focusing exclusively on managing instructional materials, assessing learners, and providing educational
support, while architectural constraints restrict access to (cid:28)nancial or contractual modules.
Last but not least, the architecture incorporates third-party systems and arti(cid:28)cial intelligence
modules that operate as autonomous agents, handling asynchronous tasks and administrative routines.
Without this automated infrastructure, ensuring continuous availability (High Availability (cid:21) 24/7)
would be unfeasible.
The core system delegates (cid:28)nancial transaction processing to a Payment System via secure API
calls. This action sequentially triggers the Billing System(cid:22)driven by webhooks(cid:22)to automatically
generate tax documents. Simultaneously, the AI system (Claude) functions as an integrated digi-
tal assistant (embedded agent): it facilitates heuristic navigation for visitors, processes Level 1 (L1)
support requests from learners using natural language processing (NLP), and optimizes work(cid:29)ows,
thereby relieving the administrator of repetitive support tasks [29, 22]. This complex matrix of micro-
delegations transforms the application from a simple web platform into an autonomous, resilient, and
high-performance software ecosystem.

4 Software Implementation
The software application architecture is based on the client-server model.The frontend uses Next.js
16 (with React 19, TypeScript, and Tailwind), running on port 3000 [36, 35]. It sends HTTP/JSON
requests to the server and receives real-time data through SSE (Server-Sent Events). The backend
is built with Spring Boot 3.5 (port 8080), providing a REST API and business logic [36, 35]. It
communicates with an external AI API (Anthropic Claude) for advanced features. Data is stored in
a MariaDB database (crm_training), with the connection e(cid:30)ciently managed via JDBC using the
HikariCP pool. The architecture clearly separates the interface from data processing. The full-stack
CRM app is for an IT training company, and it’s based on two independent layers that communicate
exclusively through REST/JSON messages:
Figure 6: General Software architecture
The distinctive feature of this architecture is the clear decoupling of business logic. The backend
is a traditional Java core built on design patterns(cid:22)developed to ensure extensibility and robustness(cid:22)
where Spring Boot acts exclusively as a web presentation layer. The domain is fully autonomous,
independently managing its schema and connection pool, while Spring serves to expose the REST API
and integrate into the overall functional framework [36, 35].
4.1 Explaining Backend Architecture
The core of the TrainingIT_site application is a robust Java domain built from scratch using clearly
de(cid:28)ned layers, where the Spring Boot framework acts strictly as a web wrapper. The autonomy of this
core is evident from startup: the main class intentionally disables automatic database con(cid:28)guration.
Consequently, the domain manages its connection pool, schema, and transactions entirely indepen-
dently. Spring intervenes only at the surface level to expose functionality via a REST API and to
inject the facade. This complete decoupling ensures that the business logic remains independent of the
framework, with the code possessing the theoretical potential to run even as a desktop application.
The architectural layering follows a classic and highly transparent path regarding traceability. Po-
sitioned at the client-facing boundary(cid:22)acting as interfacing vectors(cid:22)are the REST controllers from
the ‘crm.web.controller‘ package (approximately sixteen in total); these components bear virtually no
complex logical responsibility beyond converting HTTP requests into domain-speci(cid:28)c calls and re-
turning clean Data Transfer Object (DTO) instances [36, 35]. They have no direct coupling to the

service layer; instead, their interaction is mediated exclusively through a single centralizing compo-
nent: ‘CrmFacade‘. This represents a pure implementation of the Facade design pattern(cid:22)a single
architectural pivot point designed to conceal the inherent complexity of backend subsystems behind
an abstraction layer. When a controller issues a request(cid:22)conceptually, such as "create a course" or
"enroll a contact"(cid:22)it is the facade that possesses the topological intelligence to delegate execution,
without the original caller ever needing to uncover the number of services, commands, or repositories
sequentially activated behind the scenes.
Directly beneath this facade layer lies the service layer (‘crm.service.*‘), housing the functional core
and the actual business logic(cid:22)a core that integrates processes for contact entities, courses, enrollments,
invoicing, metrics analysis, reviews, and technical support. Each service is structurally con(cid:28)gured as
a Singleton, with instantiation accessed via the classic ‘getInstance()‘ call(cid:22)a design decision mirrored
in ‘AppCon(cid:28)g‘ (elegantly optimized using the Bill Pugh idiom to ensure thread safety without explicit
synchronization) and in the management of ‘DatabaseConnection‘. For state mutations requiring
encapsulation as atomic, self-contained units of execution(cid:22)such as instantiating a contact, processing
an enrollment, or transitioning a sales opportunity to a di(cid:27)erent stage of the funnel(cid:22)the Command
pattern is employed, orchestrated by its own ‘CommandInvoker‘. Further down the stack, access to
the persistence layer is intelligently bifurcated: on one hand, Repository classes operate directly with
domain objects, o(cid:27)ering a highly abstracted, business-oriented interface; on the other, the underlying
DAO (Data Access Object) [36, 35] instances communicate directly with the MariaDB instance using
raw JDBC statements. No traces of JPA or Hibernate are found in this ecosystem; all transactional
interaction relies on explicit SQL queries(cid:22)a choice that, while introducing some syntactic verbosity,
provides absolute, deterministic control over performance [36, 35].
However, the element that lends a genuine architectural identity to this backend lies in the rich-
ness and organic intersection of various design patterns structurally interwoven within the code. A
centralized Observer mechanism, implemented as an EventBus, intercepts asynchronous noti(cid:28)cations
whenever a critical state change occurs in the system; at this point, specialized consumers (listeners)
react in a completely decoupled manner: one module logs the entry in the audit trail, another trig-
gers the onboarding email, a third generates the (cid:28)scal document, while a (cid:28)nal subsystem dynamically
recalculates the lead’s score [16, 18]. This scoring algorithm itself employs the Strategy pattern(cid:22)an
abstraction allowing for dynamic switching between linear evaluation logic and a complex strategy tai-
lored to the B2B segment, without altering the immutability of the rest of the codebase. The contact
data validation process sequentially traverses a Chain of Responsibility structure (successively verifying
email and phone number compliance, entity type, and GDPR constraints); the noti(cid:28)cation subsystem
is generated via Factory mechanisms that dynamically arbitrate between email and SMS channels,
while complex object graphs are assembled using dedicated Builder implementations. The entire as-
sembly of components is interconnected during the initial execution phase by ‘CrmRuntimeCon(cid:28)g‘,
a class that orchestrates the domain bootstrapping process, asynchronously registers observers, and
exposes the main facade as a managed bean within the Spring IoC container.
The resulting con(cid:28)guration yields a highly cohesive backend where each functional responsibility
occupies a clearly de(cid:28)ned domain, rendering the execution (cid:29)ow of a request perfectly predictable:
the path proceeds linearly from the controller, through the facade and into the service layer, before
being picked up by commands or repositories and (cid:28)nally reaching the DAO and database persistence(cid:22)
a dynamic complemented by asynchronous events branching out laterally. Ultimately, what we are
dealing with is a veritable "living manual"(cid:22)a practical compendium of design patterns rigorously
implemented within the architecture of a real-world production application.

4.1.3 Persistence infrastructure.
The sovereignty and autonomy of the domain layer warrant a separate conceptual discussion. The
‘DatabaseConnection‘ component is con(cid:28)gured as a Singleton that exclusively manages the HikariCP
connection pool, using parameters extracted from ‘AppCon(cid:28)g‘ (such as maximum size, idle connec-
tions, allocation timeouts, and deterministic lifecycle) [13, 15]. During the bootstrapping phase, the
‘WebSchemaInitializer.ensureTables()‘ call programmatically executes the ‘schema.sql‘ script, allowing
the application to auto-generate its own relational schema within the MariaDB instance. Precisely
because the Spring framework’s automatic ‘DataSource‘ is deliberately disabled, the entire persistence
management resides exclusively within the domain core(cid:22)an irrefutable empirical argument for the
previously described structural autonomy [13, 15].
4.1.4 AI Integration
AI integration is implemented as an optional module featuring graceful degradation capabilities.
The ‘crm.web.ai‘ package encapsulates the ‘ClaudeClient‘ class(cid:22)a lightweight architectural wrapper
around the o(cid:30)cial Anthropic SDK(cid:22)alongside the ‘AiService‘ component; the latter powers features
such as course recommendations, sales process assistance, the conversational chatbot, and language
localization. A particularly elegant architectural detail lies in the strict dependency on the ‘AN-
THROPIC_API_KEY‘ environment variable: if the key is missing, the client instantiates with a
‘null‘ value, the ‘isEnabled()‘ method predictably returns ‘false‘, and subsequent calls trigger a speci(cid:28)c
exception (‘AiUnavailableException‘ (cid:25) 503) rather than causing a catastrophic system crash [2, 25].
The rest of the software ecosystem continues to function seamlessly, providing a textbook example of
graceful degradation and loose coupling regarding an external dependency [2, 25].
4.1.5 The mass reporting and analysis subsystem
The ReportService/ReportController functional pairing generates binary exports in Excel (using the
Apache POI library) and PDF (via OpenPDF) formats, while the EmployeeExcelImporter compo-
nent orchestrates the reverse operation(cid:22)speci(cid:28)cally, the bulk import of employee entities from a pre-
formatted spreadsheet. This operational layer clearly demonstrates that the backend(cid:22)far transcending
the simplistic pattern of CRUD operations exposed via a REST interface(cid:22)delivers advanced capabil-
ities for analytical reporting and high-volume batch processing [2, 25].
4.1.6 Security System
To resolve any potential cognitive dissonance regarding the claims made in Chapter 1 concerning
the "Defense in Depth" concept, a point of utmost technical candor is required: within the actual
topology of the current codebase, the authentication model is implemented in a minimalist fashion
(residing strictly client-side via ‘localStorage‘ persistence), the CORS policy in ‘WebCon(cid:28)g‘ is restric-
tively con(cid:28)gured for the Next.js server origin only, and mechanisms typical of a genuine production
environment(cid:22)such as data-at-rest encryption, MFA protocols, server-side RBAC, or immutable audit
logs(cid:22)currently represent only strategic directions for future development [22]. Ultimately, the sys-
tem stands as a genuine academic demonstration of applied software architecture and design patterns,
rather than a hardened, secure instance ready for industrial-scale production deployment.

6 Conclusions
The fundamental objective of this work was the design and implementation of a comprehensive Cus-
tomer Relationship Management (CRM) system for the TrainingIT platform; this project served as a
concrete, empirical vehicle for investigating software architecture structures and the practical applica-
tion of object-oriented design patterns. The resulting modular system comprises a backend component
developed in Java using Spring Boot 3.5(cid:22)with deterministic data persistence in a MariaDB database
via native JDBC statements and a HikariCP-managed connection pool(cid:22)and a standalone frontend
instance (a single-page application implemented in Next.js 16), with the two subsystems interfacing
exclusively through a strict REST/JSON contract.
At the frontend subsystem level, the same principle of radical decoupling governs the entire de-
sign logic: a strictly stateless security and authentication model residing entirely on the client side
and secured via access-(cid:28)ltering gateways layered by user role; a single, abstracted, and strongly typed
gateway for channeling all network calls; operational state management handled natively via the React
framework’s internal tools(cid:22)contextually supported by custom events and Context instances(cid:22)thereby
avoiding the introduction of a cumbersome global library from the outset; real-time data synchroniza-
tion based on Server-Sent Events protocols; and, as a distinctive feature, a live linguistic localization
engine powered by Arti(cid:28)cial Intelligence algorithms(cid:22)all these functionalities being built upon a set of
external dependencies deliberately kept to an absolute minimum.
The retrospective analysis was also undertaken with a necessary measure of critical honesty(cid:22)a fact
that constitutes, in itself, a valuable methodological contribution of the work. Certain discrepancies
between the theoretical conceptual model and the actual technological implementation were explicitly
identi(cid:28)ed and cataloged, without any attempt at concealment: the formal model of actors and use
cases appears considerably denser and richer than the software system actually delivered; the data
model adopts a deliberately "anemic" structure, with foreign keys managed in a rudimentary fashion
as manually handled ‘Long‘ identi(cid:28)ers(cid:22)to the detriment of the advanced associations typical of a
classic ORM; the ‘MeditationSession‘ entity perpetuates an anachronistic naming convention inherited
from a pre-existing project template, whereas renaming it to ‘TrainerSession‘ would clearly be more
appropriate; and the ‘GdprValidator‘ component encapsulates a completely inert conditional branch(cid:22)
a genuine "silent bug" that never a(cid:27)ects the validation state and requires urgent remediation during
a future refactoring session.
The project exhibits clear structural limitations(cid:22)factors that, in fact, precisely de(cid:28)ne its future
development trajectory. The authentication mechanism exists in a minimalist form and operates
exclusively on the client side(cid:22)an approach suitable for an academic demonstration but inadequate
for a genuine production environment. While the (cid:28)nancial transaction processing and noti(cid:28)cation
channels (email and SMS) are structurally complete, they remain disconnected from actual external
providers (gateways). Consequently, the primary strategic development goals focus on: bolstering
security by enforcing role-based access control and session validation on the server; integrating o(cid:30)cial
APIs for payment processing and messaging; reconciling the system’s heterogeneous role taxonomy;
and addressing speci(cid:28)c defects identi(cid:28)ed within the codebase.
In conclusion, the CRM system developed for the TrainingIT platform fully achieves its initially
established fundamental objective. We are dealing with a fully functional, end-to-end application
whose intrinsic value lies less in an excessive abundance of super(cid:28)cial features and considerably more
in its remarkable architectural clarity: a software ecosystem where every responsibility occupies a
strictly de(cid:28)ned place, where design patterns are deliberately and demonstrably implemented, and
where remaining vulnerabilities have been mapped with the utmost integrity(cid:22)thereby providing the
ideal epistemic foundation for ongoing development e(cid:27)orts.

The (cid:28)rst contribution is the demonstration of a radically decoupled architecture, in which the backend
